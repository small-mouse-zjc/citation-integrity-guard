# 数值来源核验与补造识别

"写得准"的核心是：正文每个数值都能回到真实来源（配置文件、实验日志、代码、数据说明、作者确认），不为段落顺畅补造数值。

## 双层核验

1. **脚本层（verify-values）**：从正文抽取"参数名为 数值"型声称，与 `sources` 文本里的数值集合比对，输出 `found_in_sources`。这是**数值集合比对**，不做语义等价判定。
2. **Agent 层（价值判断）**：确认找到的数值是否真是同一参数、同一条件、同一单位。例如正文"学习率 0.001"与配置"lr: 0.001"是同一参数；但正文"准确率 0.95"与日志里另一个模型的 0.95 不能混用。

## 补造的三种典型

- **顺手圆整**：配置是 0.0017，正文写 0.002——脚本比对数值集合时找不到 0.002，标为 unsupported。
- **无中生有**：来源里根本没有某项数值，正文为完整补了一个。
- **张冠李戴**：数值在来源里存在，但属于另一个实验条件（脚本会判 found，须 Agent 语义核对发现）。

第三种脚本抓不到，必须靠 Agent 结合来源定位判断——这就是 `evidence.source_location` 存在的意义。

## 处置流程

| 结果 | 处置 |
|------|------|
| found + 语义一致 | 保留，记录来源定位 |
| found + 语义不符 | 改正数值或条件，记录差异 |
| unsupported（找不到） | 回到原始配置/日志核对；确属补造则删除或改回真实值；来源确实缺失则标入 gaps 追问作者 |
| 配置冲突（两来源不一致） | 列明冲突来源，交作者裁定，不擅自选一个 |

## 参数表对齐

`build-param-table` 生成的参数表每行须有 `source`。`missing_source` 的参数不得进入正文数值声称，除非作者确认来源。正文数值与参数表取值须一致——Agent 在成稿前做最后一次交叉核对。
